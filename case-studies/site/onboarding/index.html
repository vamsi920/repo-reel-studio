Onboarding agent · October 2026

Our setup assistant can now connect itself to a locked-down bank, and it no longer claims things it has not done.

The setup assistant chats with a new customer's engineer, learns their tools and rules, and connects their systems. We tested it on a simulated bank we built, with a second AI playing the engineer. A bank is a hard case: a private network and strict security rules.

  • 5 of 5final runs connected the bank's own code system (first round: 0)
  • 71–88%of the engineer's facts learned (first round: 35%)
  • 0false "connected" claims after the first round
  • 4 of 5final runs also connected the bank's issue tracker

What we found

  • At first the app refused the bank's private network addresses, so nothing connected.
  • It now asks about network, security rules and team on its own.
  • The app, not the assistant's word, decides when a step is done.
  • A second visit asks only about what it does not already know.

Where we still fall short

  • Results vary run to run, and a second visit can repeat an earlier mistake.
  • A typical session still wastes 17 to 34 empty AI replies.
  • Once it changed a setting for the whole computer; only a written rule stops that today.

Bottom line: Setup works on a hard customer in our lab and reports honestly. Before real customers, it should run in a sealed-off space so it cannot change their computers.

Full technical write-up, for engineers

Module 05 · Onboarding agent · internal study, five rounds, 2026-10-13

Can Neo register itself into a bank it has never seen?

The onboarding agent is how NeoDevEx learns a new company: it chats with an engineer, works out their stack, network and rules, connects their systems, and asks when it is stuck. We built a simulated regulated bank behind an authenticated corporate proxy, with a self-managed GitLab, an on-prem Jira Data Center and a Nexus mirror on internal hostnames, and let a simulated engineer onboard Neo into it. Four other personas tested a small startup, a pasted token, a corrected answer and a second visit. In round 1 the agent could not connect a single internal system (the app refused the hostnames), learned 35% of what the bank engineer knew, and told her GitLab was connected when it was not. After the fixes this study forced, the agent connected the bank's GitLab in 5 of 5 final runs and Jira Data Center in 4 of 5, checked through the bank's own proxy, learned 71–88% of the facts, and made no false "connected" claim in any session after round 1. Connections now also reach the agent itself, so it can use them.

Northwind Bank, the environment under test

A small Node server plays the bank. From the agent's machine, nothing internal is reachable without going through the proxy, and the proxy needs a service account.

What exists

  • An authenticated HTTP proxy (407 without the service account). The machine running the agent is configured with it, as a bank's platform team would do.
  • TLS inspection: HTTPS tunnels to internal hosts are refused, so internal services answer only over HTTP through the proxy.
  • gitlab.northwind.internal (self-managed GitLab API), jira.northwind.internal (Jira Data Center REST, Server deployment), nexus.northwind.internal and an intranet wiki.
  • No inbound traffic, so no webhooks. Every request is logged, which is how we know what the agent actually reached.

What the engineer knows (17 facts)

  • Java 21, Spring Boot, Gradle; TypeScript and React with npm.
  • GitLab CI, merge requests with two approvals, CAB for production; dev, UAT and prod.
  • The proxy, TLS inspection, no inbound, the Nexus mirror, a read-only Postgres replica.
  • PCI-DSS, EU-only data and model traffic, 40 engineers in London and Pune.
  • She does not know the proxy password ("IAM issues it").

Gaps this study found, and what we changed

Every fix below is in the app, has tests, and was re-run against the scenario that exposed it.

  1. A bank's own GitLab could not be connected at all

    Finding

    The connection form refused *.internal and private-network hosts. That guard exists to stop the cloud proxy being aimed at internal addresses, and the cloud cannot reach them anyway. So every internal system in a regulated company was unconnectable. S4 spent 15 minutes on it.

    Fix

    Self-hosted providers accept company-internal hosts. The cloud still refuses to call them. The check runs from the machine that runs the agent, inside the company network, through its own proxy and certificate settings: the credential goes to that machine as a file (never in a command or log), curl tries HTTPS then HTTP, and a failure comes back as plain advice (DNS, proxy auth, untrusted TLS, wrong token).

    Effect

    Bank log: gitlab.northwind.internal /api/v4/version 200, jira.northwind.internal /rest/api/2/myself 200. GitLab verified 5/5 final runs.

  2. Connections never reached the agent

    Finding

    A saved connection lived only in the cloud database. The agent-server, which runs the agent's commands, never heard of it, so the agent could not use the GitLab it had just "connected".

    Fix

    A verified connection is synced to the agent-server's secrets as named variables (for example GITLAB_SELF_MANAGED_ACCESS_TOKEN), for new conversations and for the running one. The agent is told the names, never the values.

    Effect

    Four variables present on the agent-server after a bank run; removed by the harness between runs.

  3. "In progress" counted as done

    Finding

    The plan accepted any status. "in_progress" read as finished, and setup completed with nothing connected (S2).

    Fix

    Statuses are normalized; unknown ones are refused. A connection step is done only when a connection for it actually works, and skipping needs a reason.

    Effect

    Refused GitHub as done when the simulated user only claimed success (S2, round 4).

  4. Any connection of a kind finished the step

    Finding

    The org's old Jira Cloud connection let a "connect Linear" step pass after the Linear form was cancelled (round 3).

    Fix

    The step must be satisfied by the provider whose form was opened for it.

    Effect

    Covered by tests; no recurrence.

  5. Setup could finish with work open, and the agent said what it hoped

    Finding

    Round 1's closing message: "Reconnected your GitHub… Connected your self-managed GitLab… Configured Google Gemini". None was true.

    Fix

    Completion is refused while steps are pending. The agent is told to report only what a result confirmed and to close with connected / skipped / next.

    Effect

    0 false "connected" claims in the 17 sessions after round 1.

  6. The interview skipped most of what matters

    Finding

    Round 1 never asked about proxy, TLS inspection, mirrors, compliance or team, and assumed the org's Jira Cloud was their tracker.

    Fix

    A discovery checklist (stack, shipping, systems and whether each is self-hosted, network, compliance, team), one question per message, and "an existing connection is not what the company uses".

    Effect

    Bank recall 35% → 71–88%.

  7. The agent planned before asking anything round 4

    Finding

    S4 went straight to a plan, connected the wrong things and never learned which tracker the company used.

    Fix

    A plan is refused until stack, delivery and systems are known, unless the user asked to skip the interview.

    Effect

    S4 round 5: interviewed first, took the correction, 100% recall.

  8. Nothing was remembered

    Finding

    Facts lived in one browser tab. The org's company profile table had zero rows: it had never been written.

    Fix

    Facts are saved to the org's company profile (newer answer wins per key) and loaded at the start of every session. The agent is told what it knows and which sections are missing.

    Effect

    S5 opens with a summary of what it knows and asks only about the gaps.

  9. Facts filed under the wrong name were thrown away

    Finding

    "ci", "proxy" and "llm" were not known sections, so those facts were rejected and the agent asked the user again or retried six times.

    Fix

    New systems and network sections, common aliases, and anything else kept under "org" rather than refused.

    Effect

    No rejected facts in round 5.

  10. A loop that cost $1.50 round 4

    Finding

    One bank run recorded the same three facts about 30 times in a row: result, empty reply, nudge, record again.

    Fix

    A record that adds nothing gets "already recorded, ask your next question" instead of a normal receipt that reads as progress.

    Effect

    Round 5 bank runs: $0.30 and $0.40, no loop.

  11. Waiting forever round 2

    Finding

    When the engineer had to get the proxy password from IAM, the agent said "I'll wait for you to confirm" and repeated it for the rest of the session. It had also just reached GitLab through that same proxy.

    Fix

    Never wait: hand it to the owner the user names, or skip with the reason, and go on. A runtime-verified internal host proves the proxy already works on the agent's machine.

    Effect

    4 of 5 final bank runs finished, skipping the model provider with a reason; the fifth was still setting up the Nexus mirror and the read-only Postgres replica when the turn limit ended it.

  12. Tasks assigned to invented people round 2

    Finding

    The agent assigned work to it-team@northwind.internal and hr-team@…, addresses nobody gave it, including "team locations".

    Fix

    Assign only to someone the user named, with the address they gave; a question they cannot answer is an open question, not a task.

    Effect

    The wording alone did not hold: three invented addresses in rounds 4–5. The app now refuses any assignee address the user did not type in the conversation. Added after round 5; covered by tests, not yet re-measured.

  13. Reconnecting tools the company does not use

    Finding

    The test org has a revoked GitHub connection, and the agent kept pushing a bank that uses GitLab to reconnect it.

    Fix

    Ask whether they still use a provider before reconnecting it; drop it if not.

    Effect

    None of the 5 final bank runs opened a GitHub form.

  14. The setup screen looked like a coding chat

    Finding

    "What do you want to build?", repository, Pull, Push and Pull Request buttons, a welcome dialog over the Begin button, a conversation titled "Onboarding Result: GitHub Reconne…", and raw JSON receipts in the chat.

    Fix

    The setup chat hides the git bar and receipts and has its own prompt; the conversation is named at creation; the welcome dialog stays off the setup screen.

    Effect

    Covered by tests.

  15. The agent changed a machine-wide setting round 5

    Finding

    Told about the Nexus mirror, one bank run ran npm config set registry https://nexus.northwind.internal/…. The local agent-server runs as the logged-in user, so that pointed npm on the whole machine at the bank's mirror, and our own deploy then failed on it.

    Fix

    Reverted with npm config delete registry (nothing else was in the file). The brief now forbids machine-wide changes (global npm, pip, git or proxy config, shell profiles, anything in the home folder): project setup goes in the workspace's own files or a proposal a human accepts. Found after round 5; not yet re-measured, and it is a rule the model has to follow, not a guard.

    Effect

    The strongest argument for running the agent in a sandbox, not as the user, in any customer install.

  16. Smaller fixes

    Finding

    Repeating connection status at the top of every message; agent writing results it had not received; a test that asserted the old "reject unknown section" rule.

    Fix

    Brief and tool-description changes, with each change measured against the next round (one that made narration worse was reverted).

    Effect

    See the open items below for what wording could not fix.

Still open

  • One wasted model call per action. The agent-server answers every client-side tool call with "dispatched to client" at once; the real result arrives later. Gemini 2.5 Flash then replies with nothing (and is nudged) or imitates a result. We moved this around with wording but never removed it: 17–34 empty replies in a typical final session. The app now hides imitated results from the user, and completion checks never trust them. The real fix is a client tool that waits for its result, in the agent SDK.
  • Run-to-run variance. The same bank persona gave recall from 71% to 88% and Jira DC verified in 4 of 5 runs. One round-4 run never asked about the tracker, and the next day's session inherited that gap.
  • The Connections page and cloud-side features still show the cloud's verdict for internal hosts ("could not call it"); only the agent's view uses the runtime check.
  • Agent profiles drop the onboarding brief at launch, and the onboarding session's phase is never advanced.
  • The agent can change the machine it runs on. A local install runs the agent as the user; only a rule in the brief stops it touching global config. Customer installs should use the sandboxed runtime.
  • No proxy connector. The agent can describe the proxy and say whether it works, but configuring one is a platform-team task, so it is handed off.

How we tested

  • An isolated NeoDevEx stack (production build, real agent-server, real Supabase, its own state folder), with the corporate proxy set on the agent's machine as a bank's platform team would.
  • A Playwright driver logs in through the test-auth suite, starts setup, fills credential forms from the persona's lab tokens (never typed into chat), and otherwise asks a second Gemini model to answer as the persona. Traces are off so no password is recorded.
  • A scorer reads the agent-server's own event log: facts recorded against each persona's ground truth (each fact matched on its own), connections the app verified, "connected" claims without a verified result, imitated results, pasted-secret leaks, empty replies, cost and time.
  • Between scenarios the harness deletes the org's company profile, the study's connections and the synced secrets, so each company starts clean (except the second-visit scenario).

What could skew this

  • The user is simulated. It sometimes improvised facts, claimed to have filled forms, or misunderstood the UI. We tightened the persona sheets twice and read every transcript; recall only counts facts on the sheet.
  • Most scenarios ran once per round; the bank ran five times on the final build. Treat single numbers as observations, not rates.
  • The fixes were made in response to these scenarios and re-measured on them. A fresh environment (a different proxy, GitHub Enterprise, Azure DevOps) would be a stronger test.
  • The bank is a lab: internal services speak plain HTTP through the proxy instead of HTTPS with a corporate CA. The runtime check handles both, and reports HTTP as insecure.
