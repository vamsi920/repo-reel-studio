Automations · October 2026

Our automations now pass all 10 tests we could run. Devin passes 7.

We gave NeoDevEx and Devin the same unattended jobs, such as fixing a bug, and let real events on a test codebase start them. Nobody watches these jobs, so they must deliver what they claim.

  • 10 / 10tests we pass now (2 of 7 at the start)
  • 7 / 10tests Devin passes (one not measured)
  • 54problems we found in our product and fixed
  • 2 swait before a scheduled job starts, down from 52–59 s (Devin: 0 s)

What we found

  • At first, one job claimed work it never did. Every job now shows whether it delivered.
  • We set up a job from one sentence in 45 seconds. Devin drafted it but never saved it.
  • When a job fails, we say so. Devin listed a failed job as a success.
  • With Google's stronger Gemini 2.5 Pro AI model, our reviews are as correct as Devin's, and only ours show proof.

Where we still fall short

  • Devin is faster to a finished code change: 57 s against our 100 s.
  • On our cheaper default model, Gemini 2.5 Flash, reviews are shallower and one suggested fix was wrong.
  • Devin is always on in its cloud. Ours needs the computer to stay on.

Bottom line: we now match Devin on getting the job done and are more honest about failures. Devin is still faster and always on.

Full technical write-up, for engineers

Module 02 · Automations · four rounds, 2026-10-08 to 2026-10-12

We built the same automations on both tools and let them loose on a real repository.

Each automation was created on NeoDevEx and on Devin with identical instructions, then triggered by a real schedule, webhook, GitHub comment, new issue, new pull request or failing CI run on a private test repository. In round 1, NeoDevEx passed 2 of the 7 scenarios it could run; after its fixes it passed all 7. Round 2 added PR review, issue triage and creating a GitHub-triggered automation in the app's own form, and re-tested everything. NeoDevEx now passes all 10 scenarios we could run on it, and Devin passes 7 of 10 (one not measured). Schedules now fire within 2 seconds, as Devin's do. On review and triage quality, Gemini 2.5 Pro with our verify-first rules matches Devin on correctness and is the only side that shows executed proof; the default Gemini 2.5 Flash still trails. Round 4 added what Devin had and we lacked: spend and rate limits, failure alerts, webhooks set up in the app, and automations that keep running after the window closes.

Devin

  • Seven GitHub event types, ten condition operators and multi-row conditions. Powerful, but several clicks per condition.
  • Searchable picker of connected repositories, so a missing repository cannot be chosen.
  • The create form reset itself and dropped typed input 6 times across the study.
  • Built-in "Reply" step posts a second comment after the agent's own (A4, A9, A10).
  • Creating from a sentence (A7) produced an excellent draft that was never saved.

NeoDevEx, after round 2

  • newOne plain-language condition per event: "title contains", "comment contains", "branch starts with". Every GitHub trigger is tied to its repository automatically.
  • newGitHub triggers can be changed in the edit dialog the same way they were made (they were read-only).

Gaps this study found, and what we changed

Every fix below shipped in NeoDevEx during the study, has tests, and was re-run against the same scenario.

  1. Runs could report success they never delivered

    Finding

    An unattended run pushed a branch, told the user it had opened a PR, and linked GitHub's "create a PR" page. The run was recorded as complete.

    Fix

    Every automation prompt carries a delivery contract: how to open the PR or comment, how to verify it exists, and a final RESULT: line. The run page reads that line and shows Delivered, Not delivered or Unverified instead of trusting the status.

    Effect

    A1 rerun: real PR #4. A8: shown as Not delivered with the reason.

  2. GitHub-triggered automations could never fire locally

    Finding

    The automation service understands GitHub events, but a local install has no public URL for GitHub to call. Every GitHub-triggered automation silently never ran.

    Fix

    A GitHub event bridge polls the repositories that GitHub-triggered automations watch (issues, comments, PRs, pushes, failed CI runs) and posts signed events to the service. It now ships in the desktop launcher and the Docker image.

    Effect

    A4: event in 11 s. A5: CI failure to run in 10 s.

  3. No trigger for failing CI

    Finding

    The service has no GitHub schema for CI results.

    Fix

    Failed workflow runs are posted to a github-ci webhook source with event workflow_run.failure, filterable by branch.

    Effect

    A5 passes: fix pushed to the PR branch, CI green.

  4. A run asked to fix a PR opened another PR

    Finding

    Version 1 of the contract always demanded a new branch, so the CI fix arrived as a second, stacked PR.

    Fix

    Contract v2: a run about an existing PR checks out that PR's branch and pushes there. Saved prompts upgrade to the current contract automatically.

    Effect

    A5 rerun: fix landed on PR #9's own branch.

  5. Transient model errors killed runs

    Finding

    Gemini's per-minute quota error ("retry in 30 s") reached the runtime labelled as a bad request, which is not retried, so the run failed after 86 s.

    Fix

    Run recovery resumes the same conversation (it keeps the triggering event) after the delay the provider asks for, at most twice, only for errors that clear on their own.

    Effect

    The A5 run resumed and delivered its fix, CI green. Recovery has since resumed a real scheduled run on its own.

  6. Creating an automation from chat did not create one

    Finding

    The chat agent knew an automation service existed but not how to use it, and wrote a GitHub Actions workflow file instead.

    Fix

    The agent's system context now carries a short recipe for creating automations: the endpoint, a cron or GitHub-event trigger, and the user's time zone. It is told not to substitute a GitHub Actions file or crontab. Automations created that way get the delivery contract added automatically.

    Effect

    A7: correct automation saved in 45 s.

  7. Comments lost their code

    Finding

    Comments posted with a quoted --body lost every word inside backticks to the shell, for example "Corrected discount logic in and …".

    Fix

    The contract gives an exact heredoc recipe, and asks for reviewer-ready reports: the failing job, expected vs actual, root cause, change, verification.

    Effect

    Applies to every automation from its next run.

  8. Smaller fixes

    Finding

    The service crashed at boot on a transient package-download error. An expired stored GitHub token stopped every GitHub trigger. The run-trace store failed when one batch held the same span twice. The UI flagged GitHub triggers as unsupported even when a receiver existed.

    Fix

    Restart with backoff. The bridge validates credentials and falls back to the machine's GitHub CLI login. Spans are de-duplicated. The UI asks the service which event sources it can receive.

    Effect

    Covered by tests.

  9. Schedules started up to a minute late round 2

    Finding

    The automation service checks schedules every 60 s and has a hard-coded 60 s throttle per automation, so A1 started 52–59 s after its minute. Devin fires on the second.

    Fix

    The service starts through a short entry point that lowers the throttle to 5 s, with the scheduler at 5 s and the dispatcher at 2 s (in dev, the desktop app and Docker).

    Effect

    Due 20:25:00, run created 20:25:00, started 20:25:02.

  10. GitHub triggers fired for every repository round 2

    Finding

    Events are matched by type and filter only. A "push" automation for repository X also ran on pushes to repository Y.

    Fix

    Every GitHub trigger carries repository.full_name == '…': built in by the form, and added to existing automations by the event bridge.

    Effect

    All 6 GitHub-triggered automations scoped; covered by tests.

  11. Review and triage quality round 2

    Finding

    Our comments found the main bug but stopped there, and one fix contradicted the issue's expected value. They were also signed "OpenHands".

    Fix

    Delivery rules v3 and v4: reproduce first, follow the value into callers, check edge cases and CI, stay in scope, one comment with required Reproduction / Findings / Fix / Verification sections, and a NeoDevEx signature. Applied to every automation.

    Effect

    With Gemini 2.5 Pro: correct fixes with executed proof. Gemini 2.5 Flash: better format, same mistakes.

  12. The create form could only make schedules round 2

    Finding

    GitHub, CI and comment triggers were reachable only through the API or chat. Hourly and custom schedules were missing, and event triggers could not be edited.

    Fix

    A schedule-or-GitHub choice, five GitHub events with one plain-language condition, hourly and custom cron, and the same controls in the edit dialog.

    Effect

    A11 created in the form and running 13 s after its first comment.

  13. Dead GitHub credentials failed silently round 2

    Finding

    Runs inherited a revoked GitHub token and failed with generic authentication errors (A8).

    Fix

    The app checks the credential every 10 minutes and shows a banner with a Fix button when GitHub rejects it. Runs retry with the machine's own GitHub login before giving up.

    Effect

    Banner shown on this install, whose stored token is revoked.

  14. Background services stayed down after a crash round 2

    Finding

    The launcher restarted a service only if it exited with an error code, not if a signal killed it.

    Fix

    Restart on any exit outside a stack shutdown.

    Effect

    Bridge killed, back in about 2 s.

Round 3: hunting for everything else

After round 2 we went looking for problems instead of waiting for scenarios to expose them: two code audits of the automation feature, a live end-to-end run of each new template, and a re-test of every fix. 23 more problems, all fixed, each with a test.

Things that silently never worked

  • fixedSwitching a Jira trigger off, or deleting it, only changed a bookkeeping row: the automation behind it kept running.
  • fixedThe Jira Bug Fixer listened for an event name Jira never sends, and cloned the Jira project key as if it were a repository.
  • fixedJira label filters raised an error on issues with no labels, which the service counts as "no match".
  • fixedThe standalone Bug Fixer webhook server looked for automations by a field the service never fills in, so it never found one.
  • fixedAn issue opened right after a poll was skipped forever: GitHub caches lists for up to 60 s and the bridge's cursor only moved forward. Found by our own live test; fixed with a 10-minute look-back window.
  • fixed"Run now" on an event-triggered automation gave the agent no event. It now picks the newest matching issue or PR, says which, and finishes the job (verified live).
  • fixedRuns given a revoked GitHub token gave up at the first 401, and ran gh outside the cloned repository. Two explicit setup steps fixed both: the same template on the same model went from posting nothing to a reproduced, correct triage in 93 s.

Things that got in the way

  • fixedEvery failed action showed two identical error toasts.
  • fixedDouble-clicking Delete sent two deletes; the second failed with another error.
  • fixedThe guided tour advanced on a timer and navigated away under an open form, losing what had been typed. It now pauses while a dialog is open or you are typing.
  • fixed"Load more" replaced every card with a skeleton and lost the scroll position.
  • fixedSearching for an automation beyond the first page said "no matches" with no way to load more.
  • fixedHealth badges stayed on "Running" after a run finished until the window was refocused.
  • fixedThe detail page showed schedules without their time zone, and editing a time kept the old schedule description.
  • fixedA deleted automation could still be opened from cache; clicks on a menu's padding opened the detail page; exports wrote 1970 start dates for runs that never started.
  • newThe repository field suggests your GitHub repositories and refuses one GitHub says does not exist (it never blocks when it cannot check).
  • newThree new templates: Changelog and Release Notes (Devin's A6 template had no NeoDevEx equivalent), Review New Pull Requests and Triage New Issues. The triage template was created through the real UI and triaged a live issue correctly.
  • newGitHub events are fetched with conditional requests, so polling every 10 s (was 20 s) costs nothing when nothing changed.

Round 4: closing Devin's feature lead

Round 3 left a short list of things Devin had and we did not: spend and rate limits, failure notifications, webhooks you can set up in the app, and automations that keep running when nobody has the app open. Round 4 built each of them, tested each live on this machine, and fixed 7 more problems found along the way.

Built to match or beat Devin

  • newSpend limits. A daily limit per automation, over a rolling 24 hours, counting the live cost of runs still going. Reaching it cancels the running run and turns the automation off; it turns itself back on when spend leaves the window.
  • newRate limit and one-at-a-time. A cap on runs per hour, and an option to cancel a new run while an earlier one is still going. Live test: 3 runs dispatched at once, limit 1, two cancelled within 9 s, each labelled "Cancelled: hourly limit".
  • newFailure alerts. A desktop notification and/or a Slack, Discord or any https webhook, sent with the app closed. A run that finished but reported RESULT: FAILED counts as a failure (Devin recorded A8, which delivered nothing, as a success). A failure that run recovery is still retrying waits. Live: alert 1 s after the failure.
  • newWebhooks in the form. "When a webhook is called" gives the automation its own webhook. The detail page shows the URL, the signing secret once, a copy-paste signed curl, and "Send test event". Live: the displayed command and the button each started a run; deleting the automation removes its webhook.
  • newKeeps running in the background. Closing the desktop window now leaves Neo in the menu bar or system tray, so schedules, GitHub triggers and limits keep working. "Open at login" starts it hidden when you sign in.
  • newA model suggestion where it matters. When the instructions describe review, triage or investigation and the chosen model is a light one, the form suggests your cheapest frontier-tier profile, one click to switch. Round 2 showed Flash missing what Pro found.

Found while building them

  • fixedA failed run said only "Remote conversation ended with error". Run rows now show the real cause from the conversation, for example a rejected model API key, with a plain fix hint.
  • fixedThe activity log showed a status but not what the run did. Each row now shows the agent's final report, expandable to the full text.
  • fixedThe "Automations" tile counted only the loaded page, so it stopped at 50.
  • fixedAn empty or partial time in the schedule form silently became 09:00.
  • fixed"Run now" on a GitHub- or webhook-triggered automation did not say what it would do. It now explains that it runs once on the newest matching item, and why it is disabled when the automation is off.
  • fixedWebhook automations were labelled "Event" with an event type of *; they now read "Webhook" and "Any event". The create dialog no longer says every automation runs "on the schedule".
  • newAn end-to-end test drives the whole webhook path in a browser against the real stack: create in the form, send a signed test event, read the run's report and outcome.

Where Devin is still ahead

  • Always on. Devin runs in its cloud. The NeoDevEx desktop app now keeps running in the background after its window closes and can open at login, but automations still need the machine to be on. A schedule that came due while it was off runs once when it is back (the service catches up), but late. A hosted (Docker) install that is kept running avoids this.
  • Depth on the default model. On Gemini 2.5 Flash our reviews stop at the first finding and one triage fix was wrong. Gemini 2.5 Pro closes the correctness gap; Devin still finds a couple more edge cases per review.
  • Speed to a pull request. A1 57 s vs 100 s; A2 2 m 50 s vs 3 m 50 s; broken CI to green 80 s vs about 4 m 30 s.
  • Breadth. Devin triggers on Slack, GitLab, Linear and seven GitHub event types, with 24 templates. NeoDevEx covers schedules, five GitHub events, CI failures, webhooks set up in the app and Jira, with 19 templates including changelog, PR review and issue triage. Both now have spend and rate limits.
  • GitHub events arrive by polling. Locally, a bridge polls GitHub every 10 s (event to run about 4–15 s), because GitHub cannot call a laptop. Devin receives webhooks.
  • Repository picker. Devin lists connected repositories in a searchable picker; ours suggests them while you type and checks the name, but only when the stored GitHub connection works.

How we tested

  • One private fixture repository (vamsi920/automation-bench): a small cart service with two planted bugs, an issue for each, and a CI workflow running npm test.
  • Eight scenarios with verbatim instructions and the same trigger semantics on both products. Devin was driven through its web app; NeoDevEx through its automation API and agent server, exactly as its own UI and chat call them. NeoDevEx's web UI requires a sign-in we did not perform on the account owner's behalf, so its new run-outcome view is covered by component tests rather than a browser session.
  • Times come from GitHub's own timestamps (comments, commits, check runs, PRs) and each product's run record.
  • Where a NeoDevEx scenario failed, we fixed the cause and re-ran the same scenario. The "at start" column keeps the first result.
  • Code quality: the automation code changed in this study ships with unit and component tests. After round 3, 3,626 tests across 421 files (automation UI, tour, scripts, hooks, routes, API guards) pass, and the project typechecks clean. Devin is closed source, so there is nothing equivalent to compare.

What could skew this

  • Each scenario ran once per product per round (A9 and A10 ran four times on NeoDevEx as rules and models changed). Timings are single observations, not distributions.
  • NeoDevEx ran on a local machine. Its default profile (Gemini 2.5 Flash) was also serving other work, which caused the rate-limit errors in round 1. For round 2 we added a Gemini 2.5 Pro profile, used only by the "(pro)" benchmark automations. Devin runs on its own infrastructure and models.
  • Devin's A3 webhook was not fired, because doing so needs the account's webhook secret.
  • A6 compares template catalogs; no template was run end to end on either product.
  • The fixes were made in response to these scenarios and re-measured on them. They are general (delivery, triggers, recovery), but a fresh set of scenarios would be a stronger test.
