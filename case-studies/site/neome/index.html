Neo ME · October 2026

Neo ME moved a small app to new code almost exactly. A medium one did not finish.

Neo ME is our tool for moving an old application onto a new framework. We tried it on real open-source apps and checked every result with our own separate tester. That tester knows nothing about Neo ME. It sends the same clicks and requests to the old and new app and compares what comes back.

  • 34 / 37steps the same in the small blog app, up from 9 / 37 on the first try
  • $7.33cost of the final small-app migration
  • 9 / 56API requests the same in the medium app when we stopped it
  • $59.13spent on the medium app before we stopped it

What we found

  • On the first try, Neo ME said "all tests pass" when only 9 of 37 pages matched the old app. Users from the old app could not log in.
  • We made Neo ME check the result itself instead of trusting the AI. It now runs both apps on the same data and compares every page, error and database table.
  • With those checks, the small blog app came out 34 of 37 the same, and old users can log in.
  • Neo ME now also fills both apps with realistic fake data and records real browser sessions to compare. Those checks caught problems the plain page check missed.

Where we still fall short

  • The medium app, a Django API, never got close. After $59 and 1,242 AI calls, only 9 of 56 requests matched.
  • Near the end the AI fixed what its own small test list covered and broke other things. Its own score went up while our tester's score went down.
  • Once, an AI call hung for about 50 minutes and only a restart freed it.
  • The AI asked for approval to start building, then built without waiting for it.
  • We did not run the hard app, an AngularJS website. It was stopped before any work began.

Bottom line: Neo ME no longer reports a migration as done when it isn't, and small apps now come across almost exactly. It cannot yet finish a medium-sized app at a sensible cost.

Neo ME · 2026-10-20 to 2026-10-21

Three real apps, an independent black-box checker, and the full bill.

We ran Neo ME (/modernize) through its real studio UI on open-source apps of rising difficulty. The agent used Neo ME's default profile, gemini/gemini-pro-latest. Every result was checked by a differential harness in case-studies/neome/bench/. It shares no code with Neo ME and had to report 100% identical on legacy-vs-legacy before we trusted it. flaskr (Flask → Express) ended at 34 / 37 independent steps identical for $7.33. The Conduit API (Django → FastAPI) characterized perfectly but did not converge: we stopped it at $59.13 with 9 / 56 requests identical. The Conduit AngularJS frontend was not run.

Django → FastAPI: what happened

Characterization worked

  • Synth read the old schema and generated 2,544 rows across 8 app tables. Both apps start every scenario on those rows.
  • The old app replayed against itself 24 / 24 identical, with all store tables identical.
  • REA recorded 4 browser scenarios on the old app twice and found all 4 unchanged.

The migration did not

  • By $40 the new API crashed on start (NameError: get_current_user), and the agent had cut its suite from 24 steps to 10.
  • From $40 to $60 it restored the 24 steps and the API started. Its own score rose from 7 to 11 of 24.
  • Over the same $10, our checker fell from 13 to 9 of 56. The agent fixed what its suite covered and broke requests the suite never sends.
  • Progress was about one difference fixed per $1–2. We stopped at the $60 checkpoint.

What still differs

  • The old app's bugs. The legacy Django app answers several API routes (comments, favorites, unknown profiles) with Django's HTML "Page not found" page. The new app returns proper JSON errors. Neo ME counts that as a difference, correctly: users of the old API saw the HTML.
  • Status codes. 403 where the old app gives 404 on the same routes.
  • Error bodies. "Article not found" wording and shape differ.
  • Data. One store difference: a new profile gets a default avatar URL where the old app stores an empty string.
  • Old users. Logging in as a user the old app created returns a different body.

What the runs exposed in Neo ME

Fixed during the study

  • fixedClaims instead of checks. Neo ME now installs its own replay harness. The studio reads the harness report and refuses "verified" unless every step is identical on fresh data, including steps that read old data and error cases.
  • fixedAgent managing servers. The harness starts both apps on the fixture, runs a scenario and stops exactly those processes. This removed the $35 thrash of run 3.
  • fixedNo real data volume. Neo ME now asks Synth for realistic rows from the old schema and loads them into both stores. Characterize and verify are refused without them.
  • fixedDatabase not compared. After every scenario both SQLite stores are compared table by table.
  • fixedBrowser behaviour not compared. REA records each browser journey on both apps and compares them. On flaskr it caught a moved stylesheet and a changed 404 reason phrase that the page check missed.
  • fixedOpting out of REA. The agent declared the JSON API "not browser-facing". An opt-out is now refused for any app with an HTTP address.
  • fixedTesting the wrong server. The agent measured Neo's own server on port 8000. The harness now refuses a port that already answers.
  • fixedSynth writing into framework tables and SQLite dates in the wrong format.
  • fixedNew launches failed with a 422. Adding a command changed the tool schema the agent-server had pinned. Synth now rides on the existing describe command.
  • fixedUnbounded spend. The studio now pauses every $10 and asks before going on. It fired at $10, 20, 30, 40, 50 and 60 on Django.
  • fixedThinking animation never played. It read a status that agent-server conversations never set.

Still open

  • openMedium apps do not converge. Django cost $59 and ended at 9 / 56.
  • openSuite too small. A 24-step suite let the agent break behaviour it did not cover. Neo ME should require a minimum coverage of routes and error cases before migration starts.
  • openHung model call. One call blocked the conversation for about 50 minutes. Pause and resume returned 409; only restarting the agent-server cleared it. The conversation then resumed from storage.
  • openApproval not enforced on files. The agent asked to start building and built before the answer. The studio can refuse to mark the step started, but it cannot stop file writes.
  • openHard app untested. No result for the AngularJS → React migration.
  • openREA's SQLite inspector needs Node 24.15 or later. The test machine had 24.14, so the agent fell back to sqlite3 .schema.

Input dominates. Each call resends the whole conversation, about 144k tokens per call on Django, almost all of it cached. Output is under 0.2% of tokens. Long runs are expensive because the history grows, not because the agent writes a lot. Token figures for flaskr runs 1 and 3, and run 3's call count, were not saved.

How we tested

  • Apps: pallets/flask examples/tutorial; gothinkster/django-realworld-example-app (Python 3.8 via uv); gothinkster/angularjs-realworld-example-app pinned to angular@1.5.11, served against a local copy of the Django API because the public demo API is gone.
  • Each migration ran through the real studio UI on a local NeoDevEx stack: pick a local folder, answer the interview cards, approve the plan and each $10 spend checkpoint. We answered as a user would and did not edit the agent's code.
  • Independent checkers, in case-studies/neome/bench/: flaskr_diff.py replays a browser-like session and compares status, redirect target, form fields and visible text; conduit_diff.py sends 56 API requests and compares JSON exactly after normalising JWTs, timestamps and slug suffixes; conduit_ui_diff.mjs is a 32-checkpoint Playwright journey for the frontend (unused). Each had to report 100% identical on two fresh copies of the old app first.
  • Costs and tokens are the agent-server's own reported metrics for the conversation.

What could skew this

  • One run per app on the final Neo ME build. A second run could land differently.
  • Neo ME changed between flaskr runs, so the runs show the effect of the fixes, not repeatability.
  • We stopped Django ourselves. With more money it might have converged; the trend at the end did not suggest so.
  • Only one model was used. A stronger coding model may do much better on Django.
  • The Django characterize report in the downloads is a later 10-step rerun. The 24 / 24 result came from the run before it and its report was overwritten.
