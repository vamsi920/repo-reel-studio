Walkthrough for pallets/flask @ 258d68b6 (detached HEAD, git status clean). I checked it two ways: by reading the code, and by running a throwaway script in /tmp against an editable install. The script logged every hook for a blueprint view that raises ValueError.

One thing to know first: at this commit there is no separate RequestContext. A single AppContext carries the request, so pushing it once and popping it once covers both "request" and "app" teardown.

1. WSGI entry

Flask.__call__ → Flask.wsgi_app app.py:1566-1625
ctx = self.request_context(environ) → AppContext.from_environ (app.py:1501).
ctx.push() ctx.py:416-444: sets the _cv_app contextvar, sends appcontext_pushed, opens the session (_get_session), then runs match_request().

2. Dispatch and the view raising

full_dispatch_request(ctx) app.py:992-1019 sends request_started, then calls preprocess_request (url_value_preprocessors, then before_request functions), then dispatch_request (app.py:966) calls the view, and the view raises.
Its except Exception calls handle_user_exception(ctx, e) app.py:865-895. The error isn't an HTTPException, so it calls _find_error_handler (src/flask/sansio/app.py:865).
If a handler exists, the exception counts as handled. Its return value goes through finalize_request as usual, no signal fires, and teardown later receives None.
If no handler exists, a bare raise re-raises the error. The finalize_request call in full_dispatch_request is skipped.

3. Back in wsgi_app: except Exception as e

It sets error = e and calls handle_exception(ctx, e) app.py:897-948, which runs these steps in order:
Captures exc_info = sys.exc_info().
got_request_exception.send(self, exception=e). This fires first, always, before the propagate check and before logging. Receivers get the original exception.
propagate = PROPAGATE_EXCEPTIONS; if that is None, it falls back to testing or debug.
If propagate is true, the exception is re-raised: no logging, no 500 response, no after_request. It leaves wsgi_app, but the finally block still runs ctx.pop(error). I confirmed this in a second script run.
Otherwise it calls log_exception(ctx, exc_info) (app.py:950), which logs "Exception on /path [GET]" via app.logger.error.
Builds InternalServerError(original_exception=e) and calls _find_error_handler for 500/InternalServerError. If a handler exists, it is called with the InternalServerError, not with the original error.
Calls finalize_request(ctx, server_error, from_error_handler=True) app.py:1021-1050:
make_response.
process_response app.py:1394-1418. This is where after_request runs, on the 500 response:
(a) ctx._after_request_functions (from after_this_request), in the order they were registered;
(b) for each name in chain(request.blueprints, (None,)), meaning the blueprint(s) first and then the app, its after_request_funcs in reverse registration order;
(c) session_interface.save_session.
The request_finished signal is sent.
Because from_error_handler=True, any exception in this step is logged as "Request finalizing failed…" and swallowed.

4. Response, then teardown

return response(environ, start_response): the Werkzeug Response calls start_response("500 …") and returns the body iterable.
The finally block then runs:
the werkzeug.debug.preserve_context hook, if one is in the environ;
should_ignore_error, which is deprecated and None by default (sansio/app.py:925). If overridden, it can set error back to None.
ctx.pop(error) ctx.py:446-504. Once the push count reaches 0, it runs:
app.do_teardown_request(ctx, exc) app.py:1420-1451: blueprint(s) first, then the app, each in reverse registration order, each called as func(exc). Then the request_tearing_down signal (exc=exc).
self._request.close().
app.do_teardown_appcontext(ctx, exc) app.py:1453-1479: teardown_appcontext_funcs in reverse registration order, each called as func(exc). Then the appcontext_tearing_down signal.
_cv_app.reset(...), then the appcontext_popped signal.
Each of these steps is wrapped in _CollectErrors helpers.py:654-683. Every callback runs even if an earlier one raises; errors are raised together at the end as a BaseExceptionGroup on Python 3.11+, or as the first error on older versions.
The argument: teardown functions get the original ValueError, not the InternalServerError, even though a 500 response was produced successfully.
wsgi_app returns the iterable. The server has the status and headers by now, but it writes the body bytes after teardown has already run.

Edge cases:

abort(404) and other HTTPExceptions go through handle_http_exception. They are not "unhandled", so no signal fires and teardown gets None.
Errors that aren't Exception subclasses (e.g. KeyboardInterrupt) hit the bare except: in wsgi_app. That sets error and re-raises: handle_exception doesn't run, no signal fires, no after_request runs, but teardown still gets that exception.
