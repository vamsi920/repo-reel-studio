It reported one well-evidenced bug family: the studio's `ConnectionCard`/`ConnectionForm` (raised by the agent's `open_connection_form`/`request_credentials` onboarding-control commands) seeds every non-secret field from the connector manifest's *default* value, never from an already-connected provider's real, saved `ConnectionRecord.config` -- so reopening the card to rotate a secret or fix a failed probe on a provider with a non-blank manifest default (PostHog's `instanceHost`, GitHub Enterprise's host, AWS Bedrock's `region`, ...) silently overwrites that saved value with the manifest default on submit, with a "success" toast and no warning. The exact same bug was already found and fixed once in the sibling `CredentialRequestSheet` component (same command, different UI surface) -- that fix's own comment explains the failure mode and has a dedicated regression test (`credential-request-sheet.test.tsx`) that `ConnectionCard`/`ConnectionForm` had no equivalent for. A second, related discrepancy in the same code: `WorkbenchCard["fields"]` (`string[] | "all"`) is documented as narrowing a `request_credentials` card to just the one secret being rotated, and `onboarding-control.ts` sets it correctly, but nothing ever reads `card.fields` -- `ConnectionForm` unconditionally renders every manifest field regardless, defeating the "narrows this sheet" contract. I verified both directly by reading the full files (`connection-form.tsx`, `connection-card.tsx`, `credential-request-sheet.tsx`, `validation.ts`, `onboarding-studio-store.ts`) rather than trusting the report at face value. I considered three approaches for the first bug: (a) duplicate `CredentialRequestSheet`'s one-time ref-guarded seeding effect directly inside `ConnectionCard`, bypassing `ConnectionForm`; (b) add the seeding logic to the shared `ConnectionForm` component itself, gated by a new optional `existingConnection` prop, so any future caller gets the fix automatically; (c) refactor `ConnectionForm` to always require the caller to pre-seed `values` externally. Picked (b): the bug is in the shared, general-purpose component (`ConnectionForm` is reused by both the studio card and the manual `/environment/connections` page), so fixing it there benefits every caller and mirrors how the codebase already centralizes this exact validation/seeding logic in `validation.ts`. (c) would have meant a bigger, riskier refactor of every caller's state ownership for no extra benefit. I initially also wired the fix into `environment-connections.tsx` (the manual connections page) and wrote a matching regression test there, but on tracing `ConnectorCard` found that page never offers a "reconfigure" affordance for an already-connected provider at all (only "Test"/"Disconnect" render once `connection` is set, no "Connect" button) -- so `existingConnection` there is always null in practice today, the wiring would be untestable/unreachable dead code, and I reverted both the wiring and that test to keep this diff scoped to the one real, reachable bug.
