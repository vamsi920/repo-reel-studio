### 2026-09-17 — auth-data-platform — two incompatible conventions for `workspaces.id` are both live in the same schema, and the identity-bootstrap path used on every conversation still has the RLS bug the other one was built to fix
- what was observed: `src/lib/data-platform/repositories/repository-identity.ts` contains two different functions for turning `(backendId, path)` into a Supabase `workspaces.id`: `ensureWorkspaceAccess` (called from `useSupabaseIdentity`, wired into `conversation.tsx` — runs on *every* conversation) passes through the caller's raw id, which is always `computeWorkspaceId(backendId, path)` from `useWorkspaceId()` (`src/hooks/use-workspace-id.ts`) — the same id the memory/activity/usage repositories (`memory-repository.ts`, `activity-store.ts`, `usage-repository.ts`) write against, and the same one the AgentOps sidecar (`scripts/agentops/supabase-store.mjs`) writes under a fixed system org (`DEFAULT_ORG_ID`). `resolvePersistenceIds` (called for Knowledge/CodeGraph generation from `generate-knowledge.ts`/`kt-graph.tsx`), by contrast, computes `orgScopedWorkspaceId(orgId, backendId, path)` = `` `${orgId}_${computeWorkspaceId(backendId, path)}` `` — a *different* id for the exact same physical workspace. The file's own comment on `orgScopedWorkspaceId` (repository-identity.ts:181-197) says this was introduced because the raw id, shared with the AgentOps-seeded row, made `workspaces` upsert's ON CONFLICT path hit an UPDATE that RLS's `has_workspace_role(id, 'admin')` policy denies for every real user — "confirmed live... a 100%-reproducing collision, not an edge case." I traced the actual RLS policies (`supabase/migrations/20260819201420_rls_orgs_workspaces.sql:56-59`, `20260819201342_rls_helper_functions.sql`) and confirmed the mechanism: `workspaces` UPDATE requires `has_workspace_role(id, 'admin')`, and a user who isn't a member of the AgentOps seed org would indeed be denied. The org-scoped id fix was applied only inside `resolvePersistenceIds`, never in `ensureWorkspaceAccess` — so the collision this comment describes as "confirmed live" for every real user should still be reproducing today on the identity-bootstrap path that gates `memory_records`/`activity_events`/`usage_events` persistence for ordinary conversations (per `ensureWorkspaceAccess`'s own docstring, that's exactly what it's supposed to unblock). Meanwhile `AGENTS.md` (repo root, "AgentOps Control Tower" section) states the opposite invariant just as explicitly: "`workspaces.id`... is always `computeWorkspaceId(backendId, path)`... Using anything else creates a second, unlinked `workspaces` row for the same real folder — invisible to every other workspace-scoped query and RLS policy in the schema... **Do not revert this to a raw-path `workspace_id`** — that was tried and found to silently orphan AgentOps data." Taken together: `orgScopedWorkspaceId` is itself "anything else" than the canonical id AGENTS.md describes, so the Knowledge/CodeGraph rows it produces are the "second, unlinked `workspaces` row for the same real folder" that same file warns against — orphaned from AgentOps' historical queries (`agentops-repository.ts`) and from the memory/activity/usage rows for the identical workspace.
- why it needs a human: the two documented "fixes" (raw id for AgentOps-linkage, org-scoped id for the RLS 42501 collision) are mutually exclusive for the same column with the schema as it stands today, and I have no Supabase credentials in this cloud sandbox to check the live `workspaces`/`workspace_members` table contents or actually reproduce either failure mode against production data before touching it. A wrong call here is not cosmetic: it either reintroduces a "100%-reproducing" RLS failure that silently degrades memory/activity/usage persistence to local-only for real signed-in users on every conversation (current state, if my read of the code is right), or it further fragments Knowledge/CodeGraph data from the rest of the platform (if scoping is extended everywhere without a matching AgentOps-side change). A real fix also isn't a small patch: making `ensureWorkspaceAccess` org-scope its id without also updating every write path that currently uses the raw `useWorkspaceId()` (memory/activity/usage/vector/artifact repositories and their calling hooks) would just move the mismatch rather than closing it, since those repositories don't currently know the org id at all (`useWorkspaceId()` is a synchronous hook; org resolution is async) — this is a multi-file, RLS-security-relevant change well past this playbook's size cap, on a repo where every push deploys to production immediately.
- suggested next step: decide (with access to the live Supabase project) which id convention `workspaces.id` should actually use going forward, then make it consistent everywhere in one coordinated change: either (a) keep the canonical raw `computeWorkspaceId(backendId, path)` per AGENTS.md, and instead fix the AgentOps-seed-org collision a different way (e.g. give the AgentOps collector a real per-org bootstrap instead of a fixed `DEFAULT_ORG_ID`, which AGENTS.md's own "Org bootstrap is a known, temporary gap" note says is the planned direction anyway), removing `orgScopedWorkspaceId` from `resolvePersistenceIds`; or (b) commit to org-scoped workspace ids everywhere, update `AGENTS.md`'s stated invariant, and propagate the org id into `useWorkspaceId()` and every repository that currently keys off it (memory, activity, usage, vector, artifact, agentops-repository's own queries). Either way, verify against the live `workspaces`/`workspace_members` tables first — check whether real, non-AgentOps-seeded workspace rows already exist under the raw id (meaning the "confirmed live" collision may already be moot for most users) before changing anything.
