Bug: the chat-input status pill shows "Disconnected" (with an error/X icon) for a whole in-progress agent turn even though the turn is genuinely running and completing successfully server-side, which could easily make a user think the run crashed and reload/abandon it unnecessarily. What I did: in a fresh no-repo conversation on the default neodevex-gemini-default profile, sent "Run `echo hello-neo-ui-test && date` in the terminal, then tell me the output" (completed cleanly, pill showed normal "Running"/"Done" states throughout), then immediately sent a second message "Open https://example.com in the browser tab and tell me the page title" in the same conversation. What I expected: the same normal Running -> Done status progression as the first turn. What actually happened: partway into the second turn the pill switched to "Disconnected" with the error/X icon and stayed there continuously through "3 actions completed" and the agent's final correct answer ("I have opened https://example.com in the browser tab. The page title is 'example.com'.") - i.e. actions kept executing and streaming into the chat transcript and the Browser tab correctly showed the loaded example.com page the whole time, so the backend connection and event delivery were clearly still working; only navigating away and reloading the conversation URL cleared the stale "Disconnected" label. Root cause: src/components/features/controls/agent-status.tsx's getStatusCode (src/utils/status.ts) hard-overrides every other status with I18nKey.CHAT_INTERFACE$DISCONNECTED whenever useUnifiedWebSocketStatus() (src/hooks/use-unified-websocket-status.ts, backed by src/contexts/conversation-websocket-context.tsx) reports anything other than "OPEN", regardless of executionStatus/taskStatus - so if that tracked connectionState briefly flips to CLOSED/CLOSING (e.g. a reconnect cycle) and then either reconnects without the context's state updating or the actual event stream keeps flowing through a different channel than the one this hook watches, the UI is stuck showing a false "Disconnected" error for the rest of the turn instead of self-correcting once real connectivity is confirmed (e.g. once new events keep arriving). Suggested fix: in getStatusCode / AgentStatus, don't let a stale webSocketConnectionState !== "OPEN" reading permanently override the status once fresh execution/task events are still visibly arriving - either have conversation-websocket-context.tsx re-verify and correct connectionState promptly on each incoming message even mid-"CLOSED", or have AgentStatus treat "still receiving live events" as evidence the connection is fine and prefer the executionStatus-derived label over a same-turn websocket blip; add a regression test that simulates a transient CLOSED->OPEN flip mid-turn and asserts the pill does not stay on CHAT_INTERFACE$DISCONNECTED once new events resume.

Suggested fix: either move a visible Save/Discard control (or at least a "You have unsaved changes" banner) next to the Language/Analytics/Sound Notifications/Title-generation controls themselves, or rename the Git Settings section's button/heading to make clear it saves the whole Application page, or split each control into its own auto-saving mutation the way Color Theme already works, so silent data loss on reload can't happen for any of these four fields.

Bug: the conversation Changes panel's Commits tab shows "No commits yet" for a workspace that genuinely has git commits, while the same panel's Diff tab (in the Files/Changes view) correctly shows real, per-file diffs for that exact repo. What I did: in a fresh no-repo conversation, asked the agent to run local bash commands only (no GitHub) to create a nested git repo inside a subdirectory of the workspace (mkdir qa-git-test && cd qa-git-test && git init && git config user.email/name, then create committed.txt, git add + git commit -m "initial commit", then append a line to committed.txt and create a new untracked.txt), then opened the conversation's Changes panel and checked both the Diff and Commits tabs. What I expected: since the Diff tab correctly discovered the nested repo and rendered accurate per-line diffs (committed.txt shown as modified, old content "line1" vs new content "line1\nline2", and untracked.txt shown as a new/added file with "new file" content), I expected the Commits tab for the same conversation to list at least the one real "initial commit" that was just made. What actually happened: the Commits tab shows the empty state "No commits yet" instead, even after clicking "Refresh files" and re-opening the tab twice. Root cause, confirmed by reading source: both src/hooks/query/use-unified-get-git-changes.ts (backs the Diff tab) and src/hooks/query/use-unified-git-commits.ts (backs the Commits tab) compute the exact same gitPath via src/utils/get-git-path.ts's getGitPath(selectedRepository, workingDir), which returns the conversation's top-level workspace working_dir whenever one is set (as it is in a no-repo conversation) — it has no way to point at the nested qa-git-test subdirectory where the actual .git lives; the fact that the Diff tab still rendered correct per-file diffs for paths under qa-git-test/ suggests the git-changes agent-server endpoint independently walks the workspace tree to find nested repos while the git-commits endpoint apparently does not (or only runs git log at the exact gitPath it's given), so the two tabs disagree about whether this workspace has any git history at all. Suggested fix: make AgentServerGitService.getGitCommits use the same repo-root discovery the git-changes endpoint already performs (or have the frontend pass along the specific repo root reported by a git change entry) instead of assuming workingDir is itself a git repo root, so the Commits tab and Diff tab agree for a real repo that lives in a subdirectory of the conversation workspace; re-verify with this exact repro (local git init in a workspace subdirectory, one real commit, then compare Commits vs Diff tabs in the same conversation).

Bug: a schedule-triggered automation whose Repository field was manually typed (not picked via the live GitHub search, which is dead per the standing INC-1 incident) silently runs against an empty/default sandbox instead of the named repository, then reports a false "Successful" status with a fabricated-looking "repository root" file listing that is not the real repo's content at all, with zero error or warning anywhere in the UI or run history. What I did: on https://neo.neodevex.com with a real authenticated session, went to Automate > "Add Automation" (the quick "New automation" modal, not a Templates card), named it "QA Manual Repo Field Test", set Instructions to "List the files in the repository root and report the count.", manually typed "vamsi920/neo-qa-fixture" into the optional "Repository (owner/repo)" text field (this field never calls the live GitHub search, unlike the Templates/Proactivation repo pickers, so it accepted the value immediately despite INC-1), left Runs as Daily, and clicked "Create automation" — it created successfully and the detail page's Configuration panel correctly showed "Repositories: vamsi920/neo-qa-fixture". I then clicked "Run now" and watched both the automation's Activity Log and its spawned conversation. What I expected: since GitHub OAuth is confirmed dead (INC-1, environment/connections shows GitHub "Failing / vamsi920 / Missing: read:user, repo"), I expected the run to either fail cleanly with a repo-clone error, or for the agent to be told the repo wasn't available so it could report that honestly — the same class of behavior already documented for Proactivation's "Run now" path (a hung interactive git-clone credential prompt). What actually happened instead was worse: the run completed in ~40s at $0.0656 and the automation's own Activity Log recorded it as "Successful" with a green checkmark; but the spawned conversation shows the agent ran `ls -a | wc -l; ls -a` and confidently reported "The repository root contains the following 8 items: ., .., .git, .venv, main.py, prompt.txt, repos_config.json, setup.sh — Total count: 8 items" — none of which are real neo-qa-fixture content (confirmed via `gh api repos/vamsi920/neo-qa-fixture/contents` which lists README.md, package.json, src, tests — completely different files); the conversation's own composer additionally shows a "Connect Repo" button, proving no repository was ever actually attached to this conversation at all. Root cause, confirmed by reading the automation's own generated dispatch script (visible in the conversation's Files tab as main.py, alongside a repos_config.json that correctly contains `[{"url": "vamsi920/neo-qa-fixture", "provider": "github"}]`, so the manually-typed value WAS threaded through to the dispatcher): main.py calls `clone_result = workspace.clone_repos(repos_config)`, prints `cloned {success_count}/{len(repos_config)} repos` and, only if there were any failures, prints (not raises) `FAILED: {...}` — this is purely informational stdout, not an exception, so when clone_repos fails (here, because there is no valid GitHub credential to clone with) the script falls straight through with `repo_dirs = []`, sends the user's prompt to the agent with no repository context and no mention that the intended repo failed to load, runs to completion, and prints "ALL_OK" at the end regardless — which is exactly why the automation service records the run as "Successful" and the agent, having no idea a repository was supposed to be there, fabricates a plausible-looking "repository root" answer from whatever bare workspace files happen to exist instead of saying it has no repository access. This dispatch script does not live in this frontend repository (it is generated by the backend automation/dispatcher service per run) so the fix belongs there, not in src/. Suggested fix: in the automation dispatcher's main.py template, treat a non-empty repos_config.json with clone_result.failed_repos non-empty (or success_count < len(repos_config)) as fatal — either raise/exit non-zero so the run is correctly marked FAILED instead of Successful, or at minimum inject an explicit "the following repositories could not be cloned: ..." notice into USER_PROMPT/context_sections so the agent (and thus the user reading the transcript) knows to treat any "repository" answer as unreliable rather than silently proceeding as if the checkout succeeded; re-verify by re-running this exact repro once GitHub OAuth is reconnected (clone should succeed and list README.md/package.json/src/tests) and again while it's still broken (run should now show FAILED with a clear reason, not a fabricated Successful listing).

MITIGATION for INC-2: clicking the home page's "Onboarding agent" widget through to "Start the setup conversation" (/environment/setup) silently fails with a misleading error and leaks a permanently orphaned agent-server conversation every time it hits the standing INC-2 Supabase-auth/org-lookup incident, instead of a clear error and no side effect. What I did: with a real authenticated session on https://neo.neodevex.com, during a window where INC-2 was actively reproducing (browser console showing repeated "[repository-identity] org_members lookup failed {code: PGRST301, message: No suitable key or wrong key type}" and "orgs insert failed" with the same code, plus 403s on "getConnection: getUser() returned no user despite an active session" for both GitHub and Jira), clicked the "Onboarding agent" widget's "Open the onboarding agent" button, then "Start the setup conversation" on the resulting /environment/setup screen, twice in a row, and once more via a scripted click with a MutationObserver/fetch wrapper attached to see exactly what happened. What I expected: either the flow works despite the incident, or it fails with a clear, honest error telling the user setup can't start right now and why. What actually happened: the "Start the setup conversation" button briefly shows its pending/"Starting" label, a toast reading only "onboarding session storage is not configured" flashes and auto-dismisses in well under a second (confirmed only by polling the DOM every 300ms after a scripted click; a real user watching normally would very plausibly miss it entirely), and the screen then silently reverts to the same "Start the setup conversation" starting screen with zero conversationId ever set and no persistent error shown anywhere - a user would reasonably conclude nothing happened and keep retrying. Each retry, however, is not actually a no-op: GET /api/conversations/search confirmed a brand-new, real conversation titled "🔧 NeoDevEx Company Setup" was created on the agent-server for every single click (4 total from this run's testing, all silently orphaned with no session row ever pointing at them, confirmed cleaned up afterward via DELETE /api/conversations/<id>, all returning 200). Root cause, confirmed by reading source: EnvironmentSetupScreen.handleStart (src/routes/environment-setup.tsx) calls createConversation first and, only in its onSuccess callback, calls startSession(response.conversation_id) to persist the onboarding_sessions row that this screen's own conversationId state depends on - so a real agent-server conversation is always created before the flow's actual gate is even checked, and there is no rollback/cleanup path if that gate then fails; useStartOnboardingSession's mutationFn (src/hooks/query/use-onboarding-session.ts, lines 64-66) throws the literal string "onboarding session storage is not configured" whenever `!orgId`, which is also just wrong wording for this failure mode - Supabase IS configured (isSupabaseConfigured and the client both exist), the actual problem is that useEnvironmentOrgId() returned no org because the org_members/orgs lookup a few layers down failed with PGRST301, which is the well-documented, currently-open INC-2 incident (see ~/.claude/neo-shared/incidents.md), not a configuration gap at all. Suggested fix: two independent, both worth doing - (1) reword the thrown error (or add a distinct one) to say something like "couldn't resolve your organization - try again in a moment" instead of the configuration-sounding message, so onError's displayErrorToast(ENVIRONMENT$ERROR_LOAD) (or a more specific toast) actually tells the user the truth, and give it a normal toast duration instead of whatever currently makes it vanish in well under a second; (2) don't call createConversation until orgId (or at least a successful startSession precondition) is confirmed available, or wrap the two calls so a startSession failure deletes the just-created conversation via the same DELETE /api/conversations/<id> path this report used for cleanup, so a user (or an automated routine) hitting this incident window doesn't accumulate orphaned, never-attached "NeoDevEx Company Setup" conversations in their sidebar every time they retry; re-verify with this exact repro (click through to "Start the setup conversation" while INC-2's PGRST301 signature is reproducing in the console) once a fix lands, confirming both a durable, legible error message and zero new conversations created on failure.
