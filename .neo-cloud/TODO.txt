Bug: `useLlmConfigured()` (src/hooks/use-llm-configured.ts) has no retry/staleness guard against a transient empty `GET /api/profiles` read, so a real, working account's new conversation can immediately show the misleading "Your LLM isn't set up yet, so conversations won't run" banner and land in a broken/unusable state during the post-restart window `.neo-cloud/incidents.md`'s INC-3 entry (~18:55-19:0x UTC today) already root-caused for `/api/settings`. What I did: with the account's `neodevex-gemini-default` profile confirmed working (per INC-10's ~16:4x UTC recovery note), started a fresh no-repo conversation from the home composer during today's unusually frequent restart window (server_info uptime observed resetting to under ~400s roughly every 5-10 minutes) and it immediately showed the red-dot "Your LLM isn't set up yet" banner, never running a turn. What I expected: the conversation to launch normally, as it had a few hours earlier per INC-10's own recovery verification. What actually happened: repeated authenticated `GET /api/profiles` calls in this same window, some 500ms apart and some issued in parallel via Promise.all, returned genuinely inconsistent results within a few seconds of each other — sometimes `{"profiles":[],"active_profile":null}`, sometimes the real `{"profiles":[{"name":"neodevex-gemini-default",...}],"active_profile":"neodevex-gemini-default"}` — so it isn't only `/api/settings` that desyncs after a restart (as INC-3's own entry documents), the profiles LIST endpoint itself can also transiently read empty. Root cause (frontend half): in `src/hooks/use-llm-configured.ts`, `hasUsableActiveProfile` is derived straight from whatever `useLlmProfiles()` currently holds, with no check for "just flipped from populated to empty" or any retry before concluding the account has no usable LLM — a single successful-but-transiently-wrong response is treated identically to a genuinely unconfigured account, so `isConfigured` flips false and both the home banner (`src/components/features/home/llm-not-configured-banner.tsx`) and (per this run's repro) conversation launch itself act on it. Suggested fix: reuse the retry-banner pattern already built for INC-8's other transient-agent-server-read glitches (Knowledge/CodeGraph/Connections) — e.g. retry the profiles fetch once before trusting a 0-profile result when a previously-non-empty cached value exists for the same backend, so a genuine restart-window race doesn't spuriously block a working account from starting a conversation. The underlying restart-triggered state reset itself is INC-3's already-tracked infra root cause, not something this repo can fix directly — this item is only the frontend-side defensive guard.
