Bug (CRITICAL, actively broken in production right now, found by neo-ui-tester-hourly during a settings-module test): saving a brand-new profile via Settings > LLM > "Add LLM Profile" silently deletes/overwrites the account's existing LLM profile instead of adding a second one alongside it, even though the UI's "Available Profiles" list and per-item Edit/Delete controls present it as a genuine multi-profile library. What I did: on the live production app (neo.neodevex.com), with the only existing profile being "neodevex-gemini-default" (model gemini/gemini-pro-latest, a real working Gemini API key, confirmed active and functional in prior sessions), clicked "Add LLM Profile", entered a new profile name "qa-test-profile" with the default free OpenHands provider/model (openhands/glm-5.2) and a placeholder API key, then clicked Save. What I expected: the profile list to now contain both "neodevex-gemini-default" and "qa-test-profile", with "neodevex-gemini-default" remaining the account's active/default profile. What actually happened: confirmed via a direct authenticated GET to the agent-server's own `/api/profiles` endpoint (not just the UI) that the server now returns exactly one profile, `{"profiles":[{"name":"qa-test-profile","model":"openhands/glm-5.2","base_url":null,"api_key_set":true}],"active_profile":"qa-test-profile"}` — "neodevex-gemini-default" is completely gone from the server's profile store, not merely hidden in the UI, and "qa-test-profile" (which only has a placeholder, non-functional API key) is now the account-wide active profile that every new conversation and automation will default to; the home composer's model pill also now reads "qa-test-profile" instead of "neodevex-gemini-default", confirming the account-wide default itself changed, not just a display glitch. Root cause guess, not confirmed by reading server code (this sandbox only has the frontend repo): `ProfilesService.saveProfile()` (src/api/profiles-service/profiles-service.api.ts) calls the SDK's `ProfilesClient.saveProfile(name, request)` against local agent-server route `/api/profiles`; either that agent-server endpoint only supports a single stored profile total regardless of the name given (a single-slot backend being presented through a plural "Available Profiles" UI built for a true multi-profile model), or the save call is unintentionally replacing the whole profile set instead of upserting one named entry — either way the frontend's "Add" affordance and Available-Profiles list are actively misleading about what the action will do to existing profiles. Suggested fix: first confirm with the agent-server/SDK team whether `/api/profiles` (or the version of `@openhands/typescript-client` this repo pins) is single-profile-only by design; if so, either restrict the Settings > LLM UI to a single-profile edit form (no "Add" implying plurality) until true multi-profile support exists server-side, or if it's meant to support multiple and this is a client/request bug, fix the save call to not clobber other profiles, and either way add a client-side confirmation dialog before any save action that would remove an existing named profile the user didn't ask to touch. This is now actively broken in production: the real account has no working default LLM profile at all until a human manually re-enters the real Gemini API key via Settings > LLM (no routine has access to that secret, and this session's own attempt to even type a placeholder test key into a new profile field was blocked by the harness's own "Secret-Store Writes" safety classifier, confirming this class of action is correctly gated from unattended agents) — filed a matching needs-human.md entry for that manual-recovery step; do not attempt to "fix forward" by having a routine create another profile until the underlying save-clobbers-existing-profiles behavior above is understood and fixed, since doing so risks losing whatever profile a human recreates in the meantime.
