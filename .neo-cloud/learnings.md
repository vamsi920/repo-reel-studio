### 2026-09-28 (~19:49-20:15 UTC) — kt-video (module-of-the-day, local neo-focus-explorer, day 3) — Watch KT live-session bug diagnostic (rules out one hypothesis, narrows the search)
- Reconfirmed the top-priority findings.txt bug (Watch KT's "Open this repository's conversation to watch KT" toast fires even with a live, fully-cloned conversation open for the exact repo+branch) one more time, this run with a completely fresh conversation created end-to-end during the run itself (not a stale/reused one): opened a new conversation attached to vamsi920/layman@main via the Open Repository picker, sent "hi", waited for "I have successfully cloned the repository and checked out the main branch", then navigated straight to `/kt/vamsi920%2Flayman%40main/p-overview?view=watch`. Toast fired immediately and again ~2 minutes later after a fresh reload — ruling out any theory that this was ever a timing race against the connected-repositories list's 10s poll.
- Diagnostic finding that RULES OUT one of the two suspected root causes in the existing findings.txt entry: fetched the new conversation's stored metadata directly (`localStorage['openhands-agent-server-conversation-metadata'][<id>]`) and confirmed it correctly held `{selected_repository: "vamsi920/layman", selected_branch: "main", git_provider: "github", workspace_mode: "new_worktree"}` — so `src/lib/knowledge/connected-repositories.ts`'s `useConnectedRepositories()` should be able to build a correct `repositoryId` ("vamsi920/layman@main") for this conversation via `src/api/agent-server-adapter.ts`'s `toAppConversation()` (which sources `selected_repository`/`selected_branch` from this exact localStorage store, not from the raw agent-server API). The conversation's `workspace.working_dir` was also confirmed real and populated (`/home/openhands/workspace/project/<id>`) via a direct authenticated GET to `/api/conversations/<id>`. Both of `useConnectedRepositories`'s two required inputs (repo/branch identity, workingDir) are therefore present and correct for this conversation — so the bug is NOT "the new conversation never gets a repositoryId/workingDir at all"; the failure has to be further downstream, inside `use-knowledge-rehydration.ts`'s live-match branch itself (`resolveCommitSha` / `generateKnowledge`) or in `useConnectedRepositories`'s own `usePaginatedConversations(100)` query not yet including this specific new conversation by the time the rehydration effect runs (not fully ruled out this run — see below).
- Harness/methodology note for next time: a raw authenticated `fetch()` straight to the agent-server host's `/api/conversations/*` endpoints (bypassing the SDK client) returns the RAW agent-server shape, which has NO `selected_repository`/`selected_branch`/populated `conversation_url`/`session_api_key` fields at all — those are purely client-side concepts (`conversation-metadata-store.ts` localStorage + `toAppConversation()`'s local construction), not server fields. Don't mistake their absence in a raw fetch for evidence of a bug — it isn't; you have to inspect the localStorage metadata store directly (as above) or the app's own React Query cache to see what the frontend actually resolves.
- Attempted but inconclusive this run: tried to catch the actual live-match attempt's network calls (`AgentServerGitService.getGitCommits` inside `resolveCommitSha`, which should hit the agent-server host directly) via `read_network_requests`, but the browser tool's network capture never showed ANY request to either `neo-agent-server.fly.dev` or containing "conversations" as an XHR/fetch (only static JS asset GETs ever appeared, even right after a fresh page load) — including for my own manual `javascript_tool` fetches that definitely completed successfully with real 200 responses. This tool's network capture appears unreliable for in-page XHR/fetch calls on this page (possibly evicted by the very large number of static asset requests this route fires, or not instrumented for fetch() at all) — don't trust "no matching request" from `read_network_requests` on `/kt/*` routes as proof a call never fired; it may just not have been captured. A future run wanting to nail this down should either add a temporary `console.log` via a local dev build, or use `read_console_messages` for the specific error text `use-knowledge-rehydration.ts`'s catch block would log (currently a bare `catch {}` with no log — see findings.txt's suggested-fix note about that gap) rather than relying on network capture.
- The conversation-panel sidebar's "No workspace" section heading (which the repo-attached test conversation appeared under) is NOT evidence of this bug — confirmed it is the expected grouping for any GitHub-repo-picker conversation (as opposed to a local-folder `selected_workspace` conversation), unrelated to `selected_repository` resolution. Do not treat "No workspace" sidebar grouping as a signal for this bug in a future run.
- cleanup: the test conversation ("Clone Layman Repository", vamsi920/layman@main) was deleted via its sidebar kebab menu > Delete Conversation > Confirm Delete; confirmed "No conversations found" afterward.

### 2026-09-29 (~01:15-01:35 UTC) — kt-video (module-of-the-day, run 7) — harness gotcha + new a11y finding on genuinely untested ground
- harness gotcha: `read_page`'s interactive-element listing showed several `kt-video-list-item` buttons with a BLANK name (`button [ref_108] type="button"` with nothing after it), which at first glance looked like "these buttons have no accessible name at all" — a plausible-looking but WRONG conclusion. Cross-checking via `javascript_tool` (`button.textContent`) showed each button's real accessible name is its full concatenated text content (e.g. "Application ArchitectureWatch KT") — not blank, just not surfaced by this particular `read_page` call for this component (possibly because the name is derived from nested `<span>` children rather than a single text node or an `aria-label`). The REAL, filed defect is narrower and different from what `read_page` alone suggested: the two spans have no space between them, so the accessible name runs the title and "Watch KT" together as one word. Lesson: when `read_page` reports an interactive element with a blank/missing name, don't treat that as proof of a missing-accessible-name bug — verify with a direct `textContent`/`aria-label` check before filing, the same way `read_page`'s reported textbox name sometimes turns out to just be placeholder text doing double duty (see the 2026-09-21 AgentOps Budgets entry for that earlier instance of the same category of gotcha).
- confirmed INC-9 (Netlify deploy lag) still open via a pure `curl`+`grep` check of the known `use-knowledge-rehydration-b6Vc6RJ2.js` chunk URL — no browser session needed for this specific check, cheaper than the browser-based repro used in runs 5/6. Worth reusing this exact one-liner at the start of any future kt-video run before spending browser/conversation budget on a live Watch KT repro: `curl -s https://neo.neodevex.com/assets/use-knowledge-rehydration-b6Vc6RJ2.js | grep -c "live rehydration failed"` — 0 means still stale, don't bother with the live repro yet.
- confirmed (again, not newly filed) the "LLM isn't set up yet" banner flashing on the very first `/conversations` load right after injecting a fresh session, then correcting itself on the next load with the real LLM profile chip showing — matches the 2026-09-22 skills-plugins-mcp entry's already-documented client-side race right after a fresh session/backend state; not a new incident.
- new finding this run (filed to findings.txt): Video KT list row buttons run the page title and "Watch KT" together with no word boundary in their accessible name — found by testing vamsi920/lets-see's Video KT tab, a repo/tab combination this routine had never opened before (`lets-see` and a third repo, `myna`, now both appear in the account's Knowledge list — `myna` not yet explored by this routine, worth a future run's attention). This is genuinely new ground, not gated by INC-9, found specifically by picking an unexplored repo instead of re-running the same `layman` repro for the 6th time.
- cleanup: no conversations, automations, or GitHub issues created this run; only read-only browsing (Knowledge/Video KT pages) plus the standard telemetry-consent dialog dismissal (opted out, matching every prior run's handling).
