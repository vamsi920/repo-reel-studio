# Standing production incidents — single source of truth

One row per distinct, externally-caused problem (dead credential, infra
misconfig, third-party outage) that no routine can root-cause-fix by writing
code. This is NOT for one-off code-fixable bugs (those go in TODO.txt/findings.txt)
or one-off design questions (those go in needs-human.md).

Every routine's FIRST step each run: read this file. For each OPEN row, do a
CHEAP liveness check (one curl/API call, a few seconds) — not a full re-
investigation. Still broken → just bump `last confirmed`. Looks fixed → don't
assume; verify properly once, then set status RESOLVED and say so in your run
log. Never re-write an existing row's full text — edit fields in place.

If a routine finds a NEW standing incident, add a new `### INC-<next number>`
row here (see `~/.claude/neo-shared/blocked-item-format.md` for the exact
format and severity rubric) instead of writing prose into needs-human.md.

The daily digest reads this file as its primary source for "is the app healthy".

### INC-5 — CRITICAL — GitHub Enterprise OAuth's shared client secret can still be sent to any attacker-named public host
- status: MITIGATED (the internal/SSRF half only -- an attacker naming an internal address, cloud-metadata IP, or IPv6/IPv4-mapped equivalent is now rejected; naming an ordinary attacker-owned public domain is still accepted, see "needs from user")
- affects: `github-oauth-start`/`github-oauth-callback` (GHES connection flow) -- and, by extension, every user of this deployment, since `GITHUB_ENTERPRISE_OAUTH_CLIENT_ID`/`_SECRET` is one shared credential pair for the whole deployment, not per-user
- first seen: 2026-09-22 (02:20 UTC, neo-hourly-fixer-cloud, auth-data-platform section run)   last confirmed: 2026-09-22 (same run)   confirmed by: neo-hourly-fixer-cloud
- needs from user: a product decision on the GHES connection flow's design -- `enterpriseHost` is free text any signed-in user (an anonymous browser session qualifies) types into Connections settings, and `github-oauth-callback` POSTs the deployment-wide `GITHUB_ENTERPRISE_OAUTH_CLIENT_SECRET` to `https://<enterpriseHost>/login/oauth/access_token`. Before this run's fix, naming an internal address there (e.g. the cloud metadata IP) leaked that secret back in the response body -- that path is now blocked. But naming an ordinary public domain the attacker controls is not distinguishable from a real customer's GHES host with the information this server has, so that variant still works: register `enterpriseHost: "attacker.example.com"`, complete the OAuth dance against a fake authorize page there, and the callback still hands that secret to the attacker's own server. Closing this needs either (a) an admin-configured allowlist of GHES hosts this deployment actually serves (env var, checked before the token POST), or (b) moving to a per-tenant client id/secret registered against each customer's own GHES instance instead of one shared pair. Either is a real behavior/config change beyond what a routine should decide unasked.
- mitigation: 2026-09-22 (neo-hourly-fixer-cloud): added `assertEnterpriseHostAllowed()` (`supabase/functions/_shared/github.ts`, reusing `assertHostAllowed` from `_shared/template.ts`) and call it in both `github-oauth-start` (before the host is ever stored) and `github-oauth-callback` (immediately before the token-exchange POST that actually sends the secret, as defense in depth). Also closed a real bypass in `assertHostAllowed` itself: it only pattern-matched textual IPv4/hostname forms, so an IPv4-mapped IPv6 literal (`::ffff:169.254.169.254`), IPv6 link-local (`fe80::/10`), unique-local (`fc00::/7`), loopback (`::1`) or unspecified (`::`) address reached the exact same blocked networks unblocked. `assertHostAllowed` now numerically decodes any bracketed IPv6 hostname and checks it (and, for IPv4-mapped addresses, re-checks the embedded IPv4 against the existing pattern list) rather than only pattern-matching text. This second fix also protects every other caller of `resolveBaseUrl`/`assertHostAllowed` (the generic connector host-override flow), not just GitHub.
- evidence: `supabase/functions/github-oauth-callback/index.ts` (pre-fix) built `githubTokenUrl(enterpriseHost)` from `github_oauth_state.enterprise_host` (attacker-supplied, stored verbatim by `github-oauth-start`) and POSTed `{client_id, client_secret, code, redirect_uri, code_verifier}` to it with no host validation at all; `_shared/template.ts`'s `BLOCKED_HOST_PATTERNS` (the existing SSRF blocklist reused for the fix) matched only textual dotted-IPv4/hostname patterns, confirmed bypassable via `new URL("http://[::ffff:169.254.169.254]/").hostname === "[::ffff:a9fe:a9fe]"` (no pattern matches that string).

### INC-7 — CRITICAL — OAuth `state` is never bound to the browser that must complete it, so an attacker can bind a victim's GitHub/Jira authorization to the attacker's own account
- status: OPEN -- deliberately NOT code-fixed this run, see below
- affects: every OAuth connect flow -- `connections-oauth-start`/`_shared/connections-oauth-complete.ts` (generic flow, github/github-enterprise/jira-cloud/any future registry provider) and the two legacy flows it wraps, `github-oauth-start`/`github-oauth-callback` and `jira-oauth-start`/`jira-oauth-callback` -- i.e. every provider connection in the app
- first seen: 2026-09-23 (03:10 UTC, neo-hourly-fixer-cloud, auth-data-platform section run)   last confirmed: 2026-09-28 (17:10 UTC, neo-hourly-fixer-cloud: cheap re-check of the code itself — repo-wide grep for `HttpOnly`/`Set-Cookie`/`SameSite` across `supabase/functions/` still returns no matches, confirming no cookie/session binding was added since the prior check; no new information changing the design-decision blocker, so still holding off per below)   confirmed by: neo-hourly-fixer-cloud
- needs from user: a product/design decision on how the callback should verify the browser completing the flow is the same one that started it. The standard fix is a double-submit cookie: `connections-oauth-start` (and `github-oauth-start`/`jira-oauth-start`) sets a short-lived, `HttpOnly`, `SameSite=Lax` cookie (e.g. a hash of `state`) alongside returning `authorizeUrl`, scoped to the Supabase functions origin so it rides along on the top-level GET redirect back from the provider; the callback (`connections-oauth-complete.ts` and both legacy callbacks) then rejects the request unless that cookie is present and matches the `state` row before doing anything else. This touches every OAuth entry/exit point in the app (6 edge functions plus the frontend's `authorizeUrl` fetch, which would need `credentials: "include"`) and is exactly the kind of core-flow, cross-cutting change this sandbox cannot exercise end-to-end (no real browser completing a real provider round-trip) -- getting the cookie scope/SameSite/CORS-credentials details wrong risks either leaving the hole open or silently breaking every connection attempt the moment it deploys, with no automated test able to catch that class of mistake. Needs a human to implement and manually verify one real connect round-trip (GitHub or Jira) in a live environment before this can safely ship.
- mitigation: none -- see above for why this run held off rather than build it blind
- evidence: `connections-oauth-start/index.ts:22,71-76,100-113` derives `userId`/`orgId` solely from the caller's own authenticated session (`getCallerUserId`/`getCallerOrgId`) and stores them in `oauth_states` keyed only by the returned `state`; `_shared/connections-oauth-complete.ts:70-91,232-255` (and identically, the legacy path, `github-oauth-callback/index.ts:44-146` against `github_oauth_state`) looks up that row by `state` alone and unconditionally trusts `stateRow.user_id`/`org_id` for the resulting token write -- nothing (no cookie, no origin header check, no re-auth prompt) ties the request completing the callback to the session that created the state row. An attacker can call `*-oauth-start` as themselves to obtain a legitimate `authorizeUrl` bound to their own org, send that URL to a victim, and if the victim authorizes it on the real provider consent screen, the resulting GitHub/Jira access token is written into the *attacker's* org's connection, not the victim's.
