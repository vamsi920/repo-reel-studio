Bug: creating a new conversation attached to a repo can silently launch with the agent-server SDK's own bare default model (gpt-5.5, no API key) instead of the account's configured LLM profile, so the conversation fails its very first turn with an unrecoverable auth error and no useful message to the user. What I did: on the live app, used the composer's Open Repository dialog to attach vamsi920/layman@main to a brand-new conversation, sent "hi" plus a one-line instruction to clone the repo, and waited; the composer showed a generic "Error" chip with no explanation and the conversation never produced a reply. I fetched the conversation directly via GET /api/conversations/<id> (X-Session-API-Key auth) and found execution_status: "error" with agent.llm.model: "gpt-5.5" and api_key: null, and GET /api/conversations/<id>/events/search showed a ConversationErrorEvent with code LLMAuthenticationError and detail "litellm.AuthenticationError: ... Incorrect API key provided: None". Two immediate retries — one plain no-repo conversation ("Say the word pong") and one repo-attached conversation (vamsi920/neo-qa-fixture@main) created moments later — both correctly launched with model "gemini/gemini-pro-latest" (the account's real neodevex-gemini-default profile) and finished/ran normally, so this is intermittent, not a permanent regression, and it is not simply "repo-attach is broken" since a repo-attached retry succeeded. What I expected: every new conversation, repo-attached or not, should always launch with the account's configured LLM profile; if that can't be resolved for any reason, the existing safety check in src/hooks/mutation/use-create-conversation.ts (the one that throws "No LLM is configured for this account..." when a named agent profile's llm_profile_ref is missing and no profile has an api_key_set) should have caught it and surfaced a clear, actionable error before ever calling createConversation. What actually happened: the conversation was created anyway and silently launched via the legacy agent_settings path with an effectively empty LLM config, producing the SDK's own bare gpt-5.5/no-key default instead. Console/network: a "Failed to load resource: 403" plus "[github-connections-repository] getConnection: getUser() returned no user despite an active session" appeared in the browser console at almost the same moment as this failed conversation was created, which is INC-8's Supabase org-resolution glitch signature — the failure may be timing-correlated with that window, though this was not proven by repeated reproduction under a deliberately-forced INC-8 window. Suspected file: src/hooks/mutation/use-create-conversation.ts — specifically the branch that handles the seeded default OpenHands agent profile (`resolvedAgentProfile?.name === WELL_KNOWN_DEFAULT_AGENT_PROFILE_NAME && resolvedAgentProfile?.agent_kind === "openhands"`, which sets `effectiveAgentProfileId = undefined` to launch via legacy agent_settings) has no equivalent safety check to the sibling branch a few lines below it (missing llm_profile_ref) that verifies at least one LLM profile has api_key_set before falling back to agent_settings; also worth checking whether `options.settings` (the Settings object passed into src/api/agent-server-adapter.ts's buildStartConversationRequest/buildConfiguredOpenHandsAgentSettings) can itself be stale/incomplete during a concurrent Supabase auth hiccup, since buildConfiguredOpenHandsAgentSettings's own empty-model guard falls back to DEFAULT_SETTINGS.llm_model (not gpt-5.5), so gpt-5.5 appearing at all suggests the agent_settings payload was missing its llm block entirely rather than just having a blank model string.

Bug: when the GitHub connection this app uses for repo/branch lookups is failing (INC-1), typing a repository into the "Open Repository" dialog and searching for its branches shows a permanent "No branches found"/"No branches available" empty state with no persistent error message, leaving the user stuck with no way to attach that repo to a conversation and no explanation why — unlike other GitHub-lookup surfaces in this app that already show a friendly "GitHub isn't connected" message for the same underlying failure. What I did: on the live app (account has INC-1's known-dead GitHub OAuth connection), opened the composer's Open Repository dialog, typed "vamsi920/layman" (found instantly from the "Most Recent" cached suggestions list, so the dialog looked fully functional), selected it, then opened the branch combobox. A toast flashed "GitHub API error (401)" and the branch dropdown showed "No branches available"; typing "main" directly into the branch field still showed "No branches found" with no way to select or free-type a value, and the Confirm button never became usable. Reproduced twice in a row a few minutes apart, both times identical. What I expected: given this exact GitRepoDropdown pattern already has a documented, shipped mitigation for a dead GitHub connection (`isGithubDisconnected` in useUserProviders, threaded through to render "GitHub isn't connected — reconnect in Environment > Connections" instead of a bare empty state — see INC-1's mitigation note), the branch dropdown should show the same kind of persistent, actionable message instead of a bare "No branches found"/"No branches available" that looks identical to a repository that genuinely has no branches. What actually happened: only a one-shot toast appeared (which scrolls away and leaves no trace) and the dropdown's own empty state never distinguishes "the fetch failed" from "there really are no branches" or "still loading." Suspected file: src/hooks/query/use-branch-data.ts — `useBranchData` only forwards `isError`/`error` from `useRepositoryBranchesPaginated` (the initial/default branch list); the moment the user types a search term, `shouldUseSearch` becomes true and the displayed branches switch to `useSearchBranches`'s `data`, but that hook's own `isError`/`error` (and the separate `useSearchBranches` call used for `defaultBranchData`) are never read or merged into the values `useBranchData` returns, so a search-specific failure is invisible to src/components/features/home/git-branch-dropdown/git-branch-dropdown.tsx's `<ErrorMessage isError={isError} .../>` — only whichever query happened to be the paginated one would ever surface an error, and in this repro the branch list is populated by search once the user types anything. A real fix likely needs `useBranchData` to OR together the error states of all three underlying queries (paginated, search, default-branch search) and to distinguish a genuine "GitHub is disconnected" case (matching the existing `isGithubDisconnected` signal used elsewhere) from a generic fetch error.
