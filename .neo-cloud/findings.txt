What I did: with a freshly exported QA session on https://neo.neodevex.com, opened /kt/vamsi920%2Flayman%40main/graph (the layman repo's CodeGraph tab) three times — immediately after login (an active INC-8 window was confirmed live at that moment via /environment/connections showing every provider as a plain "Connect"), then again via a direct cold URL navigation, then a third time about 9 minutes later after /environment/connections had self-healed back to the correct GitHub/Jira "Failing" baseline (ruling out INC-8 as the cause) — and all three loads showed the identical "Graph analysis failed... needs a live workspace session" error with an identical pair of browser-level "Failed to load resource: the server responded with a status of 400" then "...404" console errors and zero app-level `[codegraph-persistence]`/`[repository-identity]` log lines (those helpers' own `logFailure()` calls never fired), meaning the failure happens inside `openExistingAnalysis`/`readJsonFromStorage`'s own try/catch (analyzer-runner.ts lines ~301-311 and ~415-444), which swallows the Storage sign-url/fetch failure with a bare `catch { return null; }` and no logging at all. What I expected: per this route's own doc comments ("the Storage-mirror fast path needs no live sandbox at all... this is what lets a cold-rehydrated entry skip straight to a graph that was already generated"), the graph should have loaded straight from the Supabase Storage mirror with no live session required. What actually happened: it fell all the way through to the `!snapshot.localPath || !conversationUrl || !sessionApiKey` guard and showed the live-session error instead, which is actively misleading since the real problem (a Storage-mirror read failure) has nothing to do with whether a live session exists. Control/contrast check: the other two repos on this account (vamsi920/lets-see, vamsi920/myna), which have never had a graph generated at all, correctly show the plain "No graph has been built for this commit yet / Build code graph" empty state on the same cold-load path — confirming this is specific to layman's already-existing snapshot row, not a universal regression. Suggested fix: add the same `console.error("[codegraph] ...", error)` logging pattern `codegraph-repository.ts`'s `logFailure()` already uses to the catch blocks in `readJsonFromStorage`/`openExistingAnalysis` (analyzer-runner.ts) so a real Storage-mirror failure leaves a diagnosable trail instead of being silently indistinguishable from "the object never uploaded", and consider a distinct error/retry state (mirroring the `coldLoadOrgError`/`codegraph-cold-load-retry` pattern already built into kt-graph.tsx for the org-lookup failure case) for "we found a record that a graph exists but couldn't load it from Storage" versus the genuine "no live session, cannot build" case — these are different problems needing different user actions (retry vs. start a conversation).
