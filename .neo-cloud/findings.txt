Bug (partial fix landed in 834218b4 -- the diagnostic half only, the user-visible misleading-error half is still open): CodeGraph's cold-load Storage-mirror fast path (`openExistingAnalysis` in src/lib/codegraph/analyzer-runner.ts, called from the cold-load effect in src/routes/kt-graph.tsx) can silently fail and fall through to the misleading "Graph analysis failed / Open this repository's conversation to build the code graph — analysis needs a live workspace session" error for a repository that genuinely has a previously-generated graph recorded in `codegraph_snapshots` (repro: vamsi920/layman, well outside any INC-8 auth-timing window; see this file's git history at 834218b4 for the full original repro with console evidence). Root cause confirmed by code inspection: `readJsonFromStorage` (analyzer-runner.ts) and `getSignedUrl` (artifact-store.ts) both collapsed every failure -- "object never mirrored" (expected/common) and a real Storage error (RLS denial, expired session, outage) alike -- into a bare `null` with zero logging, so there was no way to tell which one happened. 834218b4 fixed that half: `getSignedUrl` now logs the real Supabase error/exception (skipping only the "not configured" short-circuit), and `readJsonFromStorage` now logs a fetch throw or any non-404 HTTP status (a plain 404 stays silent -- normal for a commit that was never analyzed). This does NOT change the user-visible behavior at all -- a real Storage-mirror failure still shows the same misleading "needs a live workspace session" message, it just now leaves a console trail explaining why. Next step for whoever picks this up: with live QA access, reproduce the layman repro above and read the new `[codegraph] readJsonFromStorage(...)` / `[artifact-store] getSignedUrl(...)` console lines to find the actual failure reason (permissions? expired signed-url TTL? a workspace/repository id mismatch between what was written at analysis time and what the cold-load path resolves via `findSnapshotWorkspaceId`?), then build the distinct error/retry state the original finding suggested -- mirroring the `coldLoadOrgError`/`codegraph-cold-load-retry` pattern already in kt-graph.tsx for the org-lookup failure case -- so "a graph exists but couldn't be loaded from Storage" (retry) is shown separately from "no live session, cannot build" (start a conversation). Suspected files: src/routes/kt-graph.tsx (the cold-load effect and its `.catch(() => null)` at the openExistingAnalysis call site), src/lib/codegraph/analyzer-runner.ts (openExistingAnalysis would need to surface which failure mode occurred, not just `null`).
