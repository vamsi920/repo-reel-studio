Bug: /environment/setup (the onboarding chat+workbench screen) permanently shows the generic, scary "Unable to load conversations because the selected agent server returned data this UI does not understand. Check the backend URL/session key and update the agent server if needed." error banner, with no recovery path, whenever the org's persisted active onboarding session (`onboarding_sessions` row, read via `useOnboardingSession` in src/hooks/query/use-onboarding-session.ts) points at a `conversation_id` the agent-server no longer has — which INC-3 in .neo-cloud/incidents.md documents happens routinely, since neo-agent-server has no persistent storage and wipes all conversations on every restart (restarts happen on every push to main, multiple times an hour). What I did: loaded a fresh QA session and navigated to /environment/setup on both desktop and mobile (375x812) viewports; confirmed via a direct authenticated fetch to `https://neo-agent-server.fly.dev/api/conversations/search` (same X-Session-API-Key the app uses) that the agent-server currently has zero conversations (`{"items":[],"next_page_id":null}`), so any stored onboarding_sessions.conversation_id from an earlier session is now stale; reloaded the page multiple times and re-navigated from /conversations (which loads fine with its own "No conversations found" empty state) back to /environment/setup. What I expected: the screen would detect that its session's conversation no longer exists on the agent-server and fall back to the "no active session, start a new one" state (the same UI shown in EnvironmentSetupScreen when `session` is null), the way any other soft-deleted/expired reference is normally handled. What actually happened: the screen got permanently stuck showing the raw validation-error banner across every reload and re-navigation I tried (both viewports), with the chat input area rendering as disabled skeleton placeholders and a "Connecting" spinner that never resolves — there is no visible way for a user to escape this screen back to a fresh onboarding start short of a support/database intervention. Console/network: no console.error was logged for this specific failure (the error only surfaces as a rendered banner, not a logged exception), and no fly.dev XHR request 4xx/5xx was visible in the network log during the failure window even though the banner was showing, consistent with the error being thrown client-side by response-shape validation rather than surfaced from a raw HTTP failure. Suspected files: src/hooks/query/use-onboarding-session.ts (`useOnboardingSession` — the query that hands back the stale `conversationId` with no existence check against the agent-server), src/routes/environment-setup.tsx (`EnvironmentSetupScreen` — feeds `session.conversationId` straight into `SetupPanes`/`WebSocketProviderWrapper` with no fallback when that conversation turns out to be gone), and src/api/conversation-service/agent-server-conversation-service.api.ts (`requireDirectConversationInfo`/`invalidConversationResponse`, lines ~269-304 and ~736-754 `getRuntimeConversation` — the generic validation-failure path this symptom matches). A reasonable fix: when the conversation lookup for an onboarding session's `conversationId` fails (404 or validation error, distinguished from a real network/auth failure), treat it the same as "no active session" — call `completeOnboardingSessionForConversation`-style cleanup (or a new `abandoned`-marking path) on that stale row and let the screen fall through to its normal "start a new session" empty state instead of surfacing the raw parse-error banner.
