Bug: /environment/setup (the onboarding chat+workbench screen) permanently shows the generic, scary "Unable to load conversations because the selected agent server returned data this UI does not understand. Check the backend URL/session key and update the agent server if needed." error banner, with no recovery path, whenever the org's persisted active onboarding session (`onboarding_sessions` row, read via `useOnboardingSession` in src/hooks/query/use-onboarding-session.ts) points at a `conversation_id` the agent-server no longer has — which INC-3 in .neo-cloud/incidents.md documents happens routinely, since neo-agent-server has no persistent storage and wipes all conversations on every restart (restarts happen on every push to main, multiple times an hour). What I did: loaded a fresh QA session and navigated to /environment/setup on both desktop and mobile (375x812) viewports; confirmed via a direct authenticated fetch to `https://neo-agent-server.fly.dev/api/conversations/search` (same X-Session-API-Key the app uses) that the agent-server currently has zero conversations (`{"items":[],"next_page_id":null}`), so any stored onboarding_sessions.conversation_id from an earlier session is now stale; reloaded the page multiple times and re-navigated from /conversations (which loads fine with its own "No conversations found" empty state) back to /environment/setup. What I expected: the screen would detect that its session's conversation no longer exists on the agent-server and fall back to the "no active session, start a new one" state (the same UI shown in EnvironmentSetupScreen when `session` is null), the way any other soft-deleted/expired reference is normally handled. What actually happened: the screen got permanently stuck showing the raw validation-error banner across every reload and re-navigation I tried (both viewports), with the chat input area rendering as disabled skeleton placeholders and a "Connecting" spinner that never resolves — there is no visible way for a user to escape this screen back to a fresh onboarding start short of a support/database intervention. Console/network: no console.error was logged for this specific failure (the error only surfaces as a rendered banner, not a logged exception), and no fly.dev XHR request 4xx/5xx was visible in the network log during the failure window even though the banner was showing, consistent with the error being thrown client-side by response-shape validation rather than surfaced from a raw HTTP failure. Suspected files: src/hooks/query/use-onboarding-session.ts (`useOnboardingSession` — the query that hands back the stale `conversationId` with no existence check against the agent-server), src/routes/environment-setup.tsx (`EnvironmentSetupScreen` — feeds `session.conversationId` straight into `SetupPanes`/`WebSocketProviderWrapper` with no fallback when that conversation turns out to be gone), and src/api/conversation-service/agent-server-conversation-service.api.ts (`requireDirectConversationInfo`/`invalidConversationResponse`, lines ~269-304 and ~736-754 `getRuntimeConversation` — the generic validation-failure path this symptom matches). A reasonable fix: when the conversation lookup for an onboarding session's `conversationId` fails (404 or validation error, distinguished from a real network/auth failure), treat it the same as "no active session" — call `completeOnboardingSessionForConversation`-style cleanup (or a new `abandoned`-marking path) on that stale row and let the screen fall through to its normal "start a new session" empty state instead of surfacing the raw parse-error banner.

Bug: every "Connect" button on /environment/connections has the identical accessible name "Connect" with nothing distinguishing which of the 35+ provider cards it belongs to, so a screen-reader user browsing by a buttons-only list (a standard screen-reader navigation mode) hears "Connect, button" repeated 30+ times in a row with no way to tell GitHub's Connect apart from GitLab's, Slack's, or Postgres's. What I did: loaded /environment/connections on the live app and ran `read_page` with `filter: "interactive"` to get the actual accessibility-tree names Chromium exposes for every control on the page. What I expected: given this same file already solves the identical problem correctly for its neighboring "docs" link two elements below (`aria-label={t(I18nKey.ENVIRONMENT$VIEW_DOCS_FOR, {provider: t(manifest.nameKey)})}`, rendering as e.g. "View docs for GitHub"), the Connect/Test/Disconnect buttons right above it should have the same treatment. What actually happened: `src/components/features/environment/connections/connector-card.tsx` renders the Connect button (line ~146-152) as `<button onClick={() => onConnect(manifest)}>{t(I18nKey.ENVIRONMENT$CONNECT)}</button>` with no `aria-label` at all — same gap for the "Test"/`ENVIRONMENT$TEST_CONNECTION` and "Disconnect"/`ENVIRONMENT$DISCONNECT` buttons a few lines above it (~120-142) — while the docs link two lines below correctly disambiguates itself per-card. Confirmed via `read_page`: the accessibility tree lists roughly three dozen buttons literally named "Connect" back to back with zero distinguishing text, exactly matching the WCAG 2.1 Success Criterion 2.4.4 (Link Purpose, In Context) failure mode for controls read out of visual context. Console/network: not applicable, this is a static markup/labeling gap, not a runtime error. Suspected file: src/components/features/environment/connections/connector-card.tsx — give the Connect/Test/Disconnect buttons the same per-card `aria-label` pattern already used for the docs link, e.g. `aria-label={t(I18nKey.ENVIRONMENT$CONNECT_PROVIDER, {provider: t(manifest.nameKey)})}` (new i18n key mirroring `ENVIRONMENT$VIEW_DOCS_FOR`'s existing `{provider}` interpolation), applied to all three buttons in that file.



Bug: clicking Connect on any OAuth-only connector that isn't configured server-side on this deployment (e.g. GitLab at /environment/connections, providerId gitlab-com, an OAuth provider with zero form fields) shows a generic, unhelpful toast reading "Edge Function returned a non-2xx status code" instead of the specific, actionable error the edge function actually returned, leaving whoever manages the deployment with zero clue what's actually missing. What I did: loaded /environment/connections on the live app and clicked the GitLab card's Connect button (three times, reproducible every time); since Chrome's own console/network logs for this call showed nothing more specific than "Failed to load resource: the server responded with a status of 500 ()", I installed a temporary window.fetch interceptor via javascript_tool to capture the real request/response and confirmed: POST https://hyirnyyqwyvplwvuekda.supabase.co/functions/v1/connections-oauth-start -> 500 {"error":"oauth_not_configured","requires":["GITLAB_OAUTH_CLIENT_ID","GITLAB_OAUTH_CLIENT_SECRET"]}. What I expected: the UI should surface that precise detail (e.g. "This connector isn't configured on this deployment yet — missing GITLAB_OAUTH_CLIENT_ID, GITLAB_OAUTH_CLIENT_SECRET") the same way src/api/git-service/local-github-service.api.ts's describeProxyError() already does for the sibling github-api-proxy edge function -- that file's own comment already documents exactly this gotcha: "supabase-js's FunctionsHttpError hardcodes error.message to 'Edge Function returned a non-2xx status code' regardless of what the function actually returned -- the real reason lives in the Response body on error.context." What actually happened: src/api/environment-service/environment-service.api.ts's invoke() helper (used by every Environment/Connections edge-function call: connections-oauth-start, connections-set-credentials, connections-disconnect, environment-probe) never received that same treatment -- on any Supabase FunctionsHttpError it does "throw new EnvironmentServiceError('edge_function_error', error.message)", discarding the real JSON body outright, so every caller (src/routes/environment-connections.tsx's handleConnect at minimum, likely the setCredentials/disconnect/probeConnection call sites too) can only ever display that same generic SDK string via displayErrorToast. Confirmed reproducible 3/3 clicks with an identical toast each time; the Connect button correctly re-enables afterward (not stuck), so this is purely a lost-information bug, not a broken interaction, and it will misfire the same way for every one of the 30+ providers on this page that isn't yet configured with real OAuth app credentials. Suspected file: src/api/environment-service/environment-service.api.ts's invoke() (~line 32-42) -- give it the same error.context-reading treatment as describeProxyError() in src/api/git-service/local-github-service.api.ts (~line 83-110), threading the edge function's real {error, requires} body (or at minimum the bare error code) onto EnvironmentServiceError.message instead of the SDK's generic string, fixing every one of this module's edge-function callers at once.
